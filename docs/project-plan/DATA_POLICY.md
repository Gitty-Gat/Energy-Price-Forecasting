# Data & Artifact Ownership Policy

This document defines which repository artifacts belong in normal Git history, which are generated pipeline outputs owned by DVC/runtime workflows, and which should be treated as local or remote storage concerns.

## Goals

- Keep the Git repository useful for code review and human collaboration.
- Keep reproducible generated artifacts out of normal source control.
- Make `dvc repro` the authority for pipeline-owned outputs.
- Preserve a small, explicit set of raw/reference inputs needed to exercise the repo in this environment.

## Source-of-truth ownership

### Keep in Git

These are treated as source inputs, code, or lightweight project metadata:

- `src/`, `tests/`, `docs/`, `.github/`, config files, packaging files
- `data/raw/`
  - prompt-month futures CSVs
  - weather inputs
  - sentiment inputs
  - scenario inputs
- `data/reference/`
  - static lookup/reference files
- roadmap / planning docs under `docs/project-plan/`

Rationale:
- The current repo and DVC stages treat `data/raw/` as existing source input, not as something the pipeline can regenerate from nothing.
- The reference files are small, deterministic, and useful for reproducibility.

### Generated outputs: do not keep in normal Git tracking

These are generated by the pipeline or local verification flows and should remain ignored by Git:

- `data/processed/`
  - e.g. `ingestion_manifest.json`, `merged_exog.csv`
- `results/`
  - forecasts
  - diagnostics
  - backtests
  - summaries
  - params

Rationale:
- These files are mutable outputs of the pipeline.
- They create noisy diffs and merge conflicts.
- DVC and reproducible commands should own regeneration.

### Local-only / ephemeral artifacts

These should remain untracked and may be deleted/recreated freely:

- `.venv/`
- `site/`
- cache directories
- ad hoc `outputs/`
- ad hoc `mlruns/` created by local experiments
- temporary virtualenvs used for CI-equivalent verification

## Current repo rules

The repository currently enforces the generated-output split through `.gitignore`:

```gitignore
data/processed/
results/
```

That means:
- generated processed/results files may exist in the working tree,
- but they should not be re-added to the Git index.

## DVC contract

The DVC pipeline currently owns these generated outputs:

- `data/processed/ingestion_manifest.json`
- `data/processed/merged_exog.csv`
- `results/forecasts/...`
- `results/diagnostics/...`
- `results/backtests/...`

Operational rule:
- if a stage output is declared in `dvc.yaml`, do not also treat it as a normal Git-tracked artifact.

## Practical rules for delegates

1. Do not re-add `data/processed/` or `results/` to Git.
2. If `dvc repro` regenerates outputs under those directories, leave them ignored unless the policy itself changes.
3. If a pipeline stage wants to claim ownership of a path that is still tracked by Git, fix the ownership conflict before calling the stage “working.”
4. If raw/reference files become too large or too volatile for Git, document that change here first before migrating policy.
5. If GitHub push/auth is restored later, revisit whether raw inputs should remain in Git or move behind DVC/LFS — but do not silently change that boundary.

## Verification cues

The quickest checks for policy drift are:

```bash
git ls-files data/processed results
```

Expected result:
- no tracked files under `data/processed/` or `results/`

```bash
git check-ignore -v data/processed/merged_exog.csv results/forecasts/run_metadata.json
```

Expected result:
- both paths are ignored by `.gitignore`

## Future policy questions

These are intentionally unresolved for now:

- whether `data/raw/` should remain in Git long-term or move behind DVC/LFS/remotes
- whether canonical sample fixtures should be split from full raw inputs
- whether published benchmark artifacts should live under releases instead of repo history

Until that decision changes, this is the active policy:
- **Git owns source inputs and reference data**
- **DVC/runtime workflows own processed data and results**
